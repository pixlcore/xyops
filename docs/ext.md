# System Extensions

## Overview

xyOps system extensions let you add features to the conductor service and the browser UI.  An extension can register custom HTTP endpoints, listen for system activity, exchange WebSocket messages, add themes and icon packs, and run custom JavaScript in the browser.

This document explains how to develop, test, and publish your own xyOps extensions.  Extensions are JavaScript modules published to NPM, with source code and product metadata hosted on GitHub.  Administrators discover and install approved extensions using the "**Marketplace**" link in the sidebar.

Plugins run as separate processes to perform tasks such as executing jobs or collecting monitoring data.  Extensions run directly inside the xyOps conductor process, with access to the application's components and data.  For developing job Plugins, see the [Plugin Development](plugins.md) and [Plugin Marketplace](marketplace.md) guides.

> [!IMPORTANT]
> System extensions are trusted application code.  They are not sandboxed, and publishing to the xyOps Marketplace is limited to trusted partners.  Please contact the xyOps team before preparing a Marketplace submission.

## Requirements

To publish your xyOps extension to the marketplace, it must:

- Be written in JavaScript and loadable as a Node.js module.
- Be published publicly on NPM using an organization scope, such as `@myorg/xyext-example`.
- Be hosted publicly on GitHub, with matching organization and repository names.
- Have a specific version published to NPM and a matching git tag.
- Be free to install and use.
- Use an [OSI-approved license](https://opensource.org/licenses) for its code, and include the required licenses and attribution for any dependencies or bundled assets.
- Declare any user data or metrics collection in its README.
- Be legal to use, including compliance with applicable licenses and terms of service.
- Be family friendly.

All submissions are reviewed by the xyOps team.  PixlCore reserves the right to reject any extension submission it deems inappropriate for the marketplace.

For local development, you will also need a development installation of xyOps with system extension support, Node.js, and NPM.  See [Local Development](#local-development) for instructions.

## Package Names and IDs

An extension has three related identifiers.  Here is how they fit together:

| Identifier | Example | Used For |
|------------|---------|----------|
| NPM package name | `@myorg/xyext-example` | The `name` in your `package.json`, and the installed dependency. |
| Marketplace ID | `myorg/xyext-example` | Your GitHub organization and repository, the Marketplace listing, and installation API calls. |
| Runtime extension ID | `myorg-xyext-example` | Configuration keys, custom HTTP routes, and WebSocket messages. |

xyOps derives the NPM package name by adding `@` to the Marketplace ID.  These names must match, so a listing for `myorg/xyext-example` installs the package `@myorg/xyext-example`.

The runtime ID is generated by removing the leading `@`, replacing runs of non-word characters with hyphens, and converting the result to lowercase.  Use simple, distinctive organization and package names to avoid collisions.  The `xyext-` package prefix is a naming convention used by the examples in this guide.

## Package Structure

Create a standard NPM package with a `package.json` file and a main JavaScript file.  Here is a minimal example:

```json
{
	"name": "@myorg/xyext-example",
	"version": "1.0.0",
	"description": "An example system extension for xyOps.",
	"author": "My Organization",
	"license": "MIT",
	"main": "index.js",
	"repository": {
		"type": "git",
		"url": "https://github.com/myorg/xyext-example"
	},
	"files": [
		"index.js",
		"public"
	],
	"publishConfig": {
		"access": "public"
	}
}
```

The examples use CommonJS, with `module.exports` exporting a single extension object.  Include runtime dependencies in `dependencies`, and make sure all JavaScript files, stylesheets, images, and other runtime assets are included in your NPM package.  The optional `files` array above includes `index.js` and a `public` directory; expand it if your extension needs other files.

Your extension's version in `package.json` is a three-part number without a leading `v`, such as `1.0.0`.  The corresponding GitHub tag and Marketplace version are `v1.0.0`.

## Extension Lifecycle

When a conductor becomes primary, xyOps reads the dependency list in `data/extensions/package.json`, loads each installed extension, injects the server-side properties described below, and calls its `init()` method if present.

Extensions are loaded when the conductor becomes primary.  They are not dynamically loaded or unloaded when their installed files change.  Installing, upgrading, or removing an extension through the Marketplace restarts the primary conductor after the NPM operation completes successfully.  Browser clients are prompted to refresh when the loaded extension versions change.

Each extension's module loading and synchronous initialization are wrapped in `try/catch`.  A failed extension is logged and skipped.  This does not automatically catch errors in later event listeners, timers, asynchronous work, or request handlers, so your extension should handle its own errors in those paths.

In a multi-conductor cluster, the primary sends its extension dependency list to authenticated peers when they connect and after successful extension changes.  Peers run `npm install` when their dependency lists differ, so the packages are available if they become primary.  Make sure all conductors can reach NPM and install your extension's dependencies.

## Server-Side APIs

xyOps adds the following properties to your exported extension object before calling `init()`:

| Property | Description |
|----------|-------------|
| `xy` | The main xyOps component.  Use this to register event listeners and access xyOps APIs. |
| `server` | The [pixl-server](https://github.com/jhuckaby/pixl-server) instance. |
| `logger` | The shared [pixl-logger](https://github.com/jhuckaby/pixl-logger) instance. |
| `config` | The configuration object at `extensions.RUNTIME_ID`, or an empty object.  Treat this as read-only. |
| `logDebug(level, message, data)` | Writes an extension debug message, with optional structured data. |

These properties are available through `this` in your extension methods.  They are injected after the module is loaded, so they are not available in code that runs at the top level of the module.

Your extension can implement any of these optional methods:

| Method | Description |
|--------|-------------|
| `init()` | Called after loading and property injection.  Register listeners, prepare data, and initialize resources here. |
| `handleRequest(args, callback)` | Handles HTTP requests routed to your runtime extension ID. |
| `handleComm(socket, data)` | Handles custom WebSocket messages from authenticated browser users. |
| `shutdown()` | Called when xyOps shuts down.  Release timers and other resources here. |

The lifecycle methods do not receive completion callbacks, and xyOps does not await a Promise returned by them.  Keep initialization and shutdown work compatible with this calling convention.

### Basic Example

Here is a complete `index.js` file for a small extension:

```js
// Example xyOps system extension.
// Server properties are injected before init() is called.

module.exports = {

	init() {
		// Use the extension logger to identify messages from this package.
		this.logDebug(5, "Example extension loaded");
		
		// Only public, JSON-friendly data should be sent to the browser.
		this.client.greeting = this.config.greeting || "Hello from xyOps!";
	},
	
	shutdown() {
		// Release any resources created by init(), such as timers.
		this.logDebug(5, "Example extension shutting down");
	},
	
	client: {
		greeting: "",
		
		init: function() {
			// This function runs in the browser, before the user logs in.
			console.log(this.greeting);
		}
	}

};
```

Note that server-side methods may use shorthand syntax, such as `init() { ... }`.  Client-side functions must use `init: function() { ... }`, as explained in [Client-Side APIs](#client-side-apis).

### Configuration

Administrators can add custom extension settings to the top-level `extensions` object in their xyOps `config.json`.  Each extension gets its own object, keyed by its runtime ID:

```json
{
	"extensions": {
		"myorg-xyext-example": {
			"greeting": "Hello from our custom extension!"
		}
	}
}
```

Merge this into the existing configuration, preserving any other extension settings.  Your extension reads the value as `this.config.greeting`.  Document all supported settings, defaults, and required credentials in your README.  Treat the supplied configuration as read-only, and restart the conductor to apply settings used during initialization.

The server-side configuration object is not automatically copied to the browser (by design).  If you need to expose a setting, copy only the public value you need into your client object or a configuration response.

### Logging

Use `this.logDebug(level, message, data)` for extension diagnostics.  Messages are written when the configured debug level is at least the requested level.  With the default xyOps log configuration, they appear in `logs/Extension.log`, with your runtime ID in the category column.

```js
// Log a startup message with structured, non-sensitive details.
this.logDebug(5, "Example extension ready", { icons: 42 });
```

Load failures also produce error and warning records.  Check `logs/Error.log` and the "**Activity**" tab if your extension is missing from the loaded set.  Avoid logging credentials, session tokens, or other sensitive data.

## System Events

Register listeners with `this.xy.on(eventName, listener)` inside your server-side `init()` method.  The following events are available:

| Event | Listener Argument | Description |
|-------|-------------------|-------------|
| `configResponse` | `resp` | Modify the public configuration response sent before login.  Added top-level properties become properties of the browser's global `app` object. |
| `configPayload` | None | Return a string of JavaScript code which will be executed as part of the browser UI bootstrap. |
| `userLoginResponse` | `resp` | Modify the response being prepared for a successful user login.  The listener receives the response object, without a separate user argument. |
| `jobCompleted` | `combo_job` | A job has completed.  Receives the combined job record and details.  Treat this as a notification; changing the object does not update the stored job. |
| `internalJobCompleted` | `job` | An internal maintenance job has completed. |
| `activity` | `data` | An activity record has been generated, including its `action` and other available metadata. |
| `serverAdded` | `server` | A worker server has connected and been added. |
| `serverUpdated` | `server` | A worker server's information has been updated. |
| `serverRemoved` | `server` | A worker server has disconnected and been removed. |

Listeners run synchronously when the event is emitted.  In particular, response hooks must modify their response objects before returning, and `configPayload` listeners must return their JavaScript strings directly.

Here is an example that publishes a small amount of public data and logs completed jobs:

```js
init() {
	// Arrow callbacks preserve the extension instance as 'this'.
	this.xy.on('configResponse', (resp) => {
		// Use a distinctive property name and include public data only.
		resp.myorgExample = { title: "Example Extension" };
	});
	
	this.xy.on('jobCompleted', (job) => {
		// Observe completion without changing the completed job record.
		this.logDebug(6, "Job completed", { id: job.id, code: job.code });
	});
}
```

The first listener makes `app.myorgExample` available in the browser.  Avoid overwriting existing response properties, and keep event handlers short so they do not delay xyOps work.  Use an asynchronous operation for slow I/O, and handle errors in its callback or Promise.

## Custom HTTP Endpoints

With the default API prefix, requests under `/api/app/ext/RUNTIME_ID/` are routed to your extension's `handleRequest(args, callback)` method.  For example:

```text
/api/app/ext/myorg-xyext-example/hello
```

The API prefix is configurable, so handlers should match the extension ID and endpoint suffix rather than assume a full URL prefix.

Your handler receives the usual [web request arguments](https://github.com/jhuckaby/pixl-server-web#args), including `args.request`, `args.response`, `args.params`, and `args.query`.  Inspect the URL and parameters to dispatch your own commands, and call the callback exactly once when the request is complete.

### Public Responses

Here is a public endpoint that returns a small JSON object.  It does not access user data:

```js
handleRequest(args, callback) {
	// Match the endpoint suffix without assuming the configured API prefix.
	const path = args.request.url.replace(/\?.*$/, '');
	
	if (!path.endsWith('/myorg-xyext-example/hello')) {
		return callback("404 Not Found", {}, "Unknown extension endpoint");
	}
	
	// A single object is serialized and returned as JSON.
	callback({ code: 0, greeting: "Hello from the example extension!" });
}
```

To return an image, stylesheet, or another custom response, pass a status, headers, and body instead:

```js
// Return plain text with an explicit content type.
callback("200 OK", { 'Content-Type': "text/plain; charset=utf-8" }, "Hello!\n");
```

See the [pixl-server-web response documentation](https://github.com/jhuckaby/pixl-server-web#sending-responses) for the complete callback contract, including buffers, streams, and manually handled responses.

### Authentication and Authorization

Extension HTTP routes do not automatically require a login.  This allows extensions to serve public assets, such as icons, but any route that reads private data or performs privileged work needs to validate the caller itself.

Use `this.xy.loadSession()` to load a user session or API key, then enforce the required permissions.  Here is an administrator-only endpoint:

```js
handleRequest(args, callback) {
	const path = args.request.url.replace(/\?.*$/, '');
	
	// Match the endpoint suffix without assuming the configured API prefix.
	if (!path.endsWith('/myorg-xyext-example/status')) {
		return callback("404 Not Found", {}, "Unknown extension endpoint");
	}
	
	// Authenticate using xyOps sessions or API keys.
	this.xy.loadSession(args, (err, session, user) => {
		if (err) {
			return this.xy.doError('session', "Authentication failed", callback);
		}
		
		// requireAdmin() validates the user/session and administrator privilege.
		if (!this.xy.requireAdmin(session, user, callback)) return;
		
		// Return only the data this endpoint is intended to expose.
		callback({ code: 0, status: "ready" });
	});
}
```

For an endpoint available to non-administrators, call `this.xy.requireValidUser(session, user, callback)` and apply the privileges and resource restrictions appropriate to the operation.  Loading a session alone does not perform all of those checks.  Validate incoming parameters as well, and use POST for operations that change data.  Session-based POST requests must also satisfy xyOps CSRF validation.

For requiring specific privileges, check `this.xy.requirePrivilege(PRIV_ID, callback)`, and return if false.  Grab an ID from the [official privilege list](privileges.md).

## Static Assets

Use `this.xy.web.addDirectoryHandler()` to serve a directory containing your extension's public assets.  The handler strips the matching URL prefix and resolves the remaining path relative to that directory.

```js
const Path = require('path');

module.exports = {

	init() {
		// Serve only the dedicated public asset directory.
		this.xy.web.addDirectoryHandler(
			/^\/extensions\/myorg-xyext-example\//,
			Path.join(__dirname, 'public'),
			{ ttl: 3600 }
		);
	}

};
```

For example, `public/background.webp` would be available at URI `/extensions/myorg-xyext-example/background.webp`.

Choose a URL prefix unique to your extension, and put only public files in the served directory.  Static directory handlers do not authenticate xyOps user sessions automatically.  Keep server source, credentials, and private configuration outside the public directory.  See [pixl-server-web static directory handlers](https://github.com/jhuckaby/pixl-server-web#static-directory-handlers) for additional options.

## WebSocket Messages

Implement `handleComm(socket, data)` to receive messages sent using the `ext_msg` command.  xyOps routes these messages only from authenticated user sockets.  The message envelope contains your runtime ID and a nested data object:

```js
// Run after login, once the browser's WebSocket is authenticated.
if (app.comm.socket && app.comm.socket.auth) {
	app.comm.socket.emit('ext_msg', {
		id: 'myorg-xyext-example',
		data: { action: 'hello from client' }
	});
}
```

The extension receives the nested object as its `data` argument:

```js
// server-side
handleComm(socket, data) {
	// Validate the command before processing the message.
	if (!data || (typeof(data) !== 'object') || (data.action !== 'hello')) return;
	
	this.logDebug(6, "Received extension message", { username: socket.username });
	
	// Send a message back to the using using the `ext_msg` command in the other direction:
	socket.send('ext_msg', {
		id: 'myorg-xyext-example',
		data: { action: 'hello from server' }
	});
}
```

The socket includes `username`, `session_id`, `admin`, and `computed` user information.  Authentication does not imply access, so check the appropriate permissions before processing privileged commands.  For sensitive operations, revalidate the current session and permissions rather than relying solely on the socket's cached information.

WebSocket messages are stateless: `handleComm()` does not receive an HTTP-style callback, and there is no automatic extension response handler in the browser.  `socket.send('ext_msg', data)` sends a message back, but you'll need to also add `handleComm` function in your client code to receive messages in that direction:

```js
client: {
	// client-side
	handleComm: function(socket, data) {
		console.log("Received message in client: ", data);
	}
}
```

## Client-Side APIs

Your extension may export a `client` object.  xyOps serializes this object into the browser bootstrap payload, preserving top-level functions using their JavaScript source.  In the browser, the objects are available in `app.extensions`:

```js
// Locate this extension's browser object by its runtime ID.
const extension = app.extensions.find((item) => {
	return item.id === 'myorg-xyext-example';
});

if (extension && extension.obj) {
	console.log(extension.obj.greeting);
}
```

If the client object has an `init` function, xyOps calls it during browser initialization.  At this point, the page and global `app` object are available, but the user has not logged in.  Use this hook to register scenes and icons or add stylesheets.  To wait until login and WebSocket authentication, so you can send user-specific requests or messages, declare a `handleLogin` function in your `client` object.  It will be passed the current user after login:

```js
client: {
	init: function() {
		// app has loaded, user not logged in yet
	},
	handleLogin: function(user) {
		// user has fully logged in and websocket is connected
	}
}
```

### Initial Configuration

Define an optional `initNewConfig` function in your `client` object to provide initial settings when an administrator clicks **Configure** for your extension on the **System Status & Maintenance** page.  xyOps calls this function when the extension has no existing configuration, and displays its return value in the JSON editor.

```js
client: {
	initNewConfig: function() {
		// Supply editable defaults for the first configuration dialog.
		return {
			enabled: true,
			greeting: "Hello from xyOps!"
		};
	}
}
```

The function receives no arguments, and `this` refers to your browser-side client object.  Return a JSON-friendly configuration object synchronously; promises are not awaited.  Use the explicit function-expression syntax shown above, following the [serialization rules](#serialization-rules).

The returned settings are only saved when the administrator clicks **Save Changes**.  Cancelling leaves the configuration unchanged, so the hook can run again on a later edit.  Existing configuration objects, including an empty `{}`, skip the hook.  If the hook is absent or returns no value, the editor starts with `{}`.

This hook supplies defaults for the per-extension editor only.  It does not run when editing the `extensions` property on the main Configuration page or initialize server-side defaults at startup.  Keep any required runtime defaults in your server-side extension code.

### Serialization Rules

Client functions must use explicit function expressions:

```js
client: {
	greeting: "Hello!",
	
	init: function() {
		// 'this' is the browser-side client object.
		this.showGreeting();
	},
	
	showGreeting: function() {
		console.log(this.greeting);
	}
}
```

Follow these rules when defining the client object:

- Use `key: function(...) { ... }` for functions, including `init`.
- Use simple JavaScript identifier names for top-level keys.
- Use JSON-friendly values for data, such as strings, numbers, arrays, and plain objects.
- Keep functions at the top level of the client object.  Nested objects and arrays are serialized as JSON.
- Make client functions self-contained.  They cannot capture server-side variables, access the injected server properties, or use Node.js APIs such as `require()` and `fs`.
- Do not put credentials or private data in the client object.  The bootstrap payload is available before login.

Shorthand methods such as `init() { ... }` do not serialize correctly in the client object.  Arrow functions also do not provide the client object as `this`; use the function-expression form shown above.

### Raw JavaScript Payloads

For code that does not fit into a client object, register a server-side `configPayload` listener.  Return the JavaScript source you want included in the bootstrap payload:

```js
init() {
	// This listener runs on the server and returns browser JavaScript.
	this.xy.on('configPayload', () => {
		return `window.MyOrgExample = {
			greet: function() { console.log("Hello from the browser!"); }
		};`;
	});
}
```

The returned code executes before `app.receiveConfig()` and before client extension initialization.  Use a distinctive global name, and avoid depending on login data or a populated `app.config` at this stage.  This hook is also suitable for defining a browser-side class.  Serialize any inserted data with `JSON.stringify()` rather than interpolating untrusted text into executable code.

## Custom Themes and Scenes

xyOps has built-in light, dark, and automatic themes.  Extensions can add custom "scenes", which appear alongside these choices in the header's theme selector.  A scene adds a class to the page's `body` element, allowing your CSS to customize its appearance.

Register your scene in the client object's `init` function:

```js
client: {
	init: function() {
		// Add a custom scene to the header theme selector.
		app.scenes.push({
			id: 'myorg-tokyonight',
			title: 'Tokyo Night',
			icon: 'city-variant',
			theme: 'dark'
		});
		
		// Scope every rule to this scene so other themes remain unaffected.
		const css = `body.scene_myorg-tokyonight {
			--background-color: #1a1b26;
			--body-text-color: #c0caf5;
			background-image: url("/extensions/myorg-xyext-example/background.webp");
			background-size: cover;
			background-attachment: fixed;
		}`;
		
		// Install the stylesheet before xyOps restores the selected scene.
		$('<style>').text(css).appendTo('head');
	}
}
```

This example assumes you registered the [static asset handler](#static-assets) and included `public/background.webp` in your package.

| Property | Description |
|----------|-------------|
| `id` | A unique scene ID.  Use a simple name suitable for a CSS class. |
| `title` | The scene's name in the theme selector. |
| `icon` | An [MDI](https://pictogrammers.com/library/mdi/) icon ID for the menu entry. |
| `theme` | Optional base theme, either `light` or `dark`.  Sets the base colors when the scene is selected. |

Selecting this scene adds a `scene_myorg-tokyonight` class to the `body` element, and xyOps remembers the choice in the user's browser preferences.  The optional `theme` property selects the appropriate base palette, so your stylesheet can focus on the colors and artwork you want to customize.

Scope your CSS to the scene's body class, and check text contrast, form controls, dialogs, and smaller screen sizes.  Scene registration occurs before xyOps restores the saved scene, so you do not need to apply it manually from your extension.

## Custom Icon Packs

The browser's global `iconFontNames` array supplies names to the standard xyOps icon picker.  To add an icon pack, provide CSS for your icons, add their names to this array, and sort the combined list.

Here is an example adding a single SVG icon using a CSS mask:

```js
client: {
	init: function() {
		// Use a unique prefix for this pack's icon names.
		const iconName = 'myorg-example-sample';
		const iconURL = '/extensions/myorg-xyext-example/sample.svg';
		
		// Match the existing MDI sizing and inherit the current text color.
		const css = `.mdi.mdi-${iconName}:before {
			content: "";
			width: 1em;
			height: 1em;
			vertical-align: -0.175em;
			background-color: currentColor;
			mask: url("${iconURL}") no-repeat center / contain;
		}`;
		
		$('<style>').text(css).appendTo('head');
		
		// Add the name to the picker and keep the master list sorted.
		iconFontNames.push(iconName);
		iconFontNames.sort();
	}
}
```

This example assumes `public/sample.svg` is served using the [static asset handler](#static-assets).  The picker stores the name `myorg-example-sample`; the rendered icon uses the CSS classes `mdi mdi-myorg-example-sample`.

For a larger pack, repeat the CSS rule and registration for each icon.  Monochrome SVG masks inherit `currentColor`, so they blend in with the built-in Material Design Icons (MDI) in light and dark themes.  Validate any dynamically generated names and URLs before inserting them into CSS.

See the [selfh.st Icon Pack](https://github.com/pixlcore/xyext-selfhst-icons) for a complete working example.  It adds 2,000+ icons and serves their SVG data through the extension's HTTP handler.

### Attribution

If an icon pack or other asset requires attribution, include the source, license, and any adaptation details in your README.  A small UI credit can also make the attribution visible where the assets are used.  For example, your client `init` function could append linked credits to the existing footer:

```js
// Append the attribution once, preserving the existing copyright text.
if (!$('#myorg_example_credit').length) {
	$('#d_footer_copyright').append(
		'<span id="myorg_example_credit"> Icons by ' +
		'<a href="https://selfh.st/icons/" target="_blank" rel="noopener noreferrer">selfh.st</a> ' +
		'(<a href="https://creativecommons.org/licenses/by/4.0/" target="_blank" rel="noopener noreferrer">CC BY 4.0</a>).</span>'
	);
}
```

The copyright footer is populated before client extensions initialize.  Adapt the credit to your actual asset source and license requirements.  The extension's code license does not replace third-party asset licenses or grant rights to their trademarks.

## Local Development

You can test an extension before publishing it to NPM or submitting it to the Marketplace.  Use a separate development conductor, preferably with a single conductor, so production workloads and peer synchronization do not interfere with your local package setup.

The following example assumes xyOps is installed in `/opt/xyops`, and your extension source is in `$HOME/git/xyext-example`.  Adjust both paths for your machine.  Run the commands using an account with permission to manage the development installation, and ensure the xyOps service account can read the source directory.

### Prepare Your Extension

Create `package.json` and `index.js` using the examples above.  If your extension has dependencies, install them in its own source directory:

```sh
cd "$HOME/git/xyext-example"
npm install
```

For a development installation of xyOps, see the [Development](dev.md) guide.

### Register the Local Package

Stop your development conductor before editing its extension registration:

```sh
cd /opt/xyops
bin/control.sh stop
mkdir -p data/extensions/node_modules/@myorg
```

Create or edit `/opt/xyops/data/extensions/package.json` and add your package to `dependencies`.  Preserve all existing entries:

```json
{
	"dependencies": {
		"@myorg/xyext-example": "1.0.0"
	}
}
```

Use the package name you plan to publish, with an exact development version matching your extension's `package.json`.  This is the conductor's extension registry, separate from the `package.json` in your source directory.

Create a symlink from the installed package location to your source directory:

```sh
ln -s "$HOME/git/xyext-example" /opt/xyops/data/extensions/node_modules/@myorg/xyext-example
```

The destination must not already contain an installed package or symlink.  Check it first if you have previously registered this extension.  On systems without symbolic links, copy the complete package directory, including its installed runtime dependencies, into the same location.

This development registration bypasses the Marketplace listing requirement.  Do not run `npm install` in `data/extensions` while relying on an unpublished development package: NPM will try to resolve the registered version from the registry, and may replace your manual setup.  Install your extension's dependencies in the source directory instead.

### Start and Test

Start your development conductor and watch the extension log:

```sh
cd /opt/xyops
bin/control.sh start
tail -f logs/Extension.log
```

Check that your startup message appears, then load the xyOps UI and inspect the browser console for client-side messages or errors.  Try your custom endpoints, themes, or icons, and check both authenticated and unauthenticated behavior where relevant.

After changing server code, restart the development conductor.  Client code embedded in your extension object also comes from the loaded server module, so restart the conductor and refresh the browser to see those changes.  When changing static assets, account for browser caching; shorter cache lifetimes are useful during development.

To remove a local development registration, stop the development conductor, remove only your package's dependency entry and symlink or copied directory, then start it again.  Preserve other extensions.

## Marketplace Data

Your GitHub repository needs a top-level `xyops.json` file using [xyOps Portable Data](xypdf.md) format.  For an extension, it identifies the Marketplace product and the version to install:

```json
{
	"type": "xypdf",
	"description": "xyOps Portable Data Object",
	"version": "1.0",
	"xyops": "1.1.3",
	"items": [
		{
			"type": "extension",
			"data": {
				"id": "myorg/xyext-example",
				"version": "v1.0.0"
			}
		}
	]
}
```

Use `extension` as the item type, and the Marketplace ID for `data.id`, without the leading `@`.  Set `data.version` to the matching git tag.  Include this file in each release tag so the Marketplace can retrieve that version's installation data.

### Minimum xyOps Version

The optional top-level `xyops` property specifies the minimum supported xyOps version.  Use a three-part version without a leading `v`, and set it to the minimum version supporting the APIs your extension uses.  The example above uses `1.1.3`.

The Marketplace stops installation and displays the required version when the user's xyOps installation is older than this value.

## README

Make sure your extension has a detailed `README.md` at the root of its GitHub repository.  Use [GitHub-Flavored Markdown](https://github.github.com/gfm/).  This file serves as the product details page when users open your extension in the Marketplace.

Your README should include:

- An English description of the features your extension adds.
- The minimum supported xyOps version and any additional runtime requirements.
- Installation instructions, including the primary conductor restart.
- Any configuration properties, defaults, and required credentials.
- A declaration of any user data or metrics collection.
- Usage examples or screenshots, where helpful.
- Licenses, attribution, and adaptation notices for third-party code and assets.

A small icon pack or theme can have a short README, provided users can understand what it adds and how to use it.

## Logo

Include a logo for the Marketplace search results.  It should be:

- Square, with a 1:1 aspect ratio.
- Alpha transparent and suitable for light and dark backgrounds.
- At least 128x128 pixels.
- PNG format.
- Named `logo.png` and stored at the root of your GitHub repository.

## License

Include a `LICENSE.md` or `LICENSE` file at the root of your repository.  The extension code must use an [OSI-approved license](https://opensource.org/licenses), identified by its [SPDX identifier](https://spdx.org/licenses/) in `package.json` and the Marketplace metadata.

Also include the required notices for dependencies and bundled assets.  Icons, fonts, artwork, and other assets may have separate licenses, so identify those clearly in your README and preserve their attribution requirements.  Use assets you have permission to distribute.

## Files

The following files should live at the root of your GitHub repository:

```text
package.json
index.js
README.md
LICENSE.md
xyops.json
logo.png
```

Your main JavaScript file may have a different name if `package.json` points to it.  The license can alternatively be named `LICENSE` or `COPYING`, with or without an extension.  Include any public asset directories and supporting source files as well.

GitHub hosts the Marketplace's README, logo, and installation metadata.  NPM supplies the executable package and its dependencies.  Check that the NPM package contains everything needed at runtime; a file present in GitHub is not necessarily included in the published package.

## Tags and NPM Publishing

Each Marketplace release needs a matching GitHub tag and published NPM version:

| Location | Example Version |
|----------|-----------------|
| `package.json` | `1.0.0` |
| NPM registry | `1.0.0` |
| GitHub tag | `v1.0.0` |
| `xyops.json` item version | `v1.0.0` |
| Marketplace `versions` entry | `v1.0.0` |

xyOps installs exact extension versions.  Marketplace versions must use the `vMAJOR.MINOR.PATCH` format; semver ranges, dist-tags such as `latest`, and prerelease suffixes are not accepted by the installation API.  This restriction applies to the registered extension version; NPM still resolves the extension's own dependencies according to its package metadata.

When preparing a release:

1. Update `package.json` and `xyops.json` to the new matching version.
2. Test the extension and inspect its package contents.
3. Commit the release files, create the version tag, and push the commit and tag to GitHub.
4. Publish the same package version publicly to NPM.
5. Submit or update the Marketplace listing.

Use [npm pack](https://docs.npmjs.com/cli/commands/npm-pack) to inspect the package before publishing:

```sh
npm pack --dry-run
```

Check that your main script, supporting modules, and runtime assets are present.  For a more complete release test, run `npm pack`, unpack the resulting tarball into a separate directory, install its runtime dependencies, and register that copy with your development conductor.  This helps catch files missing from the published package that a source-directory symlink would hide.

After committing the release files, tag and push the version:

```sh
git tag v1.0.0
git push
git push origin v1.0.0
```

Publish from your extension's source directory using an NPM account authorized for the organization:

```sh
npm publish --access public
```

See [publishing scoped public NPM packages](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages/) for account setup and publishing authentication requirements.

NPM does not allow replacing a published package name and version combination.  Publish a new version for changes, and keep existing release tags stable so the GitHub metadata continues to describe the package users install.  See [npm publish](https://docs.npmjs.com/cli/commands/npm-publish) for details.

## Marketplace Submission

Once you have arranged publishing with the xyOps team and published your release to GitHub and NPM, head over to the [xyOps Marketplace repository](https://github.com/pixlcore/xyops-marketplace).

Make a pull request adding your extension metadata as a new object at the end of the `rows` array in `marketplace.json`.  Here is an example:

```json
{
	"id": "myorg/xyext-example",
	"title": "Example Extension",
	"author": "My Organization",
	"description": "Add a custom theme and icon pack to xyOps.",
	"versions": ["v1.0.0"],
	"type": "extension",
	"license": "MIT",
	"tags": ["Extension", "Themes", "Icons"],
	"requires": [],
	"created": "2026-09-30",
	"modified": "2026-09-30"
}
```

Here are descriptions of the properties:

| Property Name | Type | Description |
|---------------|------|-------------|
| `id` | String | Your GitHub organization and repository joined with a slash.  Must match the NPM package name without its leading `@`. |
| `title` | String | The extension's display name in the Marketplace. |
| `author` | String | The publisher's company or individual name. |
| `description` | String | A short description displayed under the title in search results. |
| `versions` | Array | Available release tags, sorted with the latest first.  Every entry must have a matching published NPM version. |
| `type` | String | Set this to `extension`. |
| `license` | String | The SPDX identifier for the extension code's open-source license. |
| `tags` | Array | Search keywords, such as `Extension`, `Themes`, or `Icons`. |
| `requires` | Array | Use `[]` for standard extensions.  Node.js and NPM are assumed; package dependencies belong in `package.json`. |
| `created` | String | Date of first publication, in YYYY-MM-DD format. |
| `modified` | String | Date of the latest release, in YYYY-MM-DD format. |

Plugin-specific fields such as `plugin_type` and job Plugin secret-vault hints are not needed for extensions.  Explain any extension credentials or external service requirements in your README.

All submissions are human-reviewed.  Please allow time for the team to review your source code, dependencies, and integration.  Publishing a package to NPM does not automatically make it available in the xyOps Marketplace.

### Publishing Updates

For an update, publish the new NPM version and matching GitHub tag, then submit a Marketplace pull request adding the tag at the front of your existing `versions` array.  Update `modified`, preserve `created`, and revise the description or tags if the features have changed.

Keep older versions listed when they remain supported.  Administrators choose an exact release from the Marketplace, and can install an update when they are ready.

## Installation APIs

The standard extension lifecycle APIs are available to administrators on the primary conductor:

| API | Required Parameters | Description |
|-----|---------------------|-------------|
| `app/create_extension` | `id`, `version` | Installs an approved Marketplace extension. |
| `app/update_extension` | `id`, `version` | Installs another approved version of an extension. |
| `app/delete_extension` | `id` | Removes the extension package registration. |

For installation and updates, `id` is the Marketplace ID, such as `myorg/xyext-example`, and `version` is an exact listed tag, such as `v1.0.0`.  The optional `restart` parameter requests a primary conductor restart after a successful operation.  The Marketplace UI always requests this restart, including for removal.

These APIs start a background internal maintenance job and return before the NPM operation finishes.  An initial `{ "code": 0 }` means the job was accepted, not that installation has completed.  The job report includes the NPM output and is available through the "**Activity**" tab.  It is also emailed to the initiating administrator when an email address and working mail configuration are available.

The installed package lives under `data/extensions/node_modules/@myorg/xyext-example`.  The APIs require the product to be listed as an extension in the Marketplace; they cannot install an arbitrary NPM package.  Use the [local development setup](#local-development) for unpublished code.

## Troubleshooting

| Symptom | What to Check |
|---------|---------------|
| Extension does not load | Confirm the dependency entry, package path, `main` script, and runtime dependencies.  Check `logs/Extension.log`, `logs/Error.log`, and Activity warnings. |
| Debug messages are missing | Check the configured debug level and log filename settings. |
| Browser bootstrap fails | Check that client functions use `key: function() { ... }`, top-level keys are simple identifiers, and data is JSON-friendly. |
| Client changes are not visible | Restart the development conductor and refresh the browser.  Check the browser console for initialization errors. |
| Static assets are missing | Check the URL prefix, public directory, NPM package contents, and cache settings. |
| Extension receives no WebSocket messages | Wait for login and socket authentication, and use `ext_msg` with the runtime ID and nested `data`. |
| Marketplace installation is rejected | Check trusted-publisher approval, `type: "extension"`, matching IDs, exact listed versions, and the minimum xyOps version. |
| NPM installation fails | Read the internal job report, verify the public package version exists, and check registry access from the conductor. |
